# 팀 결정 문서 (Team Decisions)

이 디렉토리는 프로젝트의 주요 제품, 기술, 운영 결정을 기록하기 위한 Single Source of Truth이다.

## 목적

- **기록**: 왜 그런 결정을 했는지 추적 가능하게 한다.
- **공유**: 개발자, 기획자, 디자이너, 팀원이 동일한 문맥에서 논의하게 한다.
- **방향성**: 프로젝트의 기술/제품/운영 방향을 일관되게 유지한다.

## 문서화 기준

아래 중 하나 이상에 해당하는 결정은 문서화한다.

- 구현 범위가 달라지는 결정
- 사용자 흐름이나 화면 구조가 바뀌는 결정
- 데이터 모델, API, 라우팅에 영향을 주는 결정
- QA 기준이나 일정에 영향을 주는 결정
- 이후 다시 논쟁이 생길 가능성이 높은 결정

단순 문구 수정, 스타일 조정, 변수명 변경처럼 영향 범위가 작은 판단은 별도 결정 문서로 남기지 않아도 된다.

또한 인덱스에 한 줄로 정리할 수 있을 정도로 간단한 결정은 [decisions/index.md](index.md)에만 등록하고, 별도의 상세 문서를 작성하지 않아도 된다.

## 범위

| 분류 | 설명 | 예시 |
|------|------|------|
| `product` | 제품, UX, 화면 흐름, 기능 범위 결정 | 구현 화면 범위, CTA 목적지, 개인화 정책, 쇼케이스 구조 |
| `technical` | 기술 및 구현 구조 결정 | 라우팅 방식, 상태 관리, 이미지 로딩, API 계약 |
| `team-ops` | 팀 운영 및 프로세스 결정 | 코드 리뷰 규칙, 회의 체계, 역할 분담 |

## 상태 관리

- `확인 필요`: 방향은 있으나 추가 확인이 필요한 결정
- `확정`: 팀이 합의하고 구현 기준으로 사용하는 결정
- `대체`: 이후 결정으로 대첸된 결정
- `폐기`: 더 이상 사용하지 않는 결정

## 파일명 규칙

```text
decisions/{분류}/YYYY-MM-DD-kebab-case-title.md
```

예시:

```text
decisions/product/2026-05-09-limit-implementation-scope.md
decisions/technical/2026-05-09-define-routing-policy.md
decisions/team-ops/2026-05-09-use-decision-records.md
```

## SSoT 원칙

- 최종 구현 기준으로 삼을 결정은 이 레포지토리에 기록한다.
- 회의록, 노션, 슬랙, 피그마 등에서 논의된 결정은 구현 전에 이곳으로 옮긴다.
- 문서화되지 않은 결정은 임시 합의로 보고, 구현 기준으로 사용하기 전 문서화한다.

## 워크플로우

1. 템플릿을 복사해 결정 문서를 생성한다.
2. 결정의 문제, 맥락, 결정, 이유, 영향, 대안을 작성한다.
3. 상태를 `확정`으로 변경하고 바로 커밋한다.
4. `main` 브랜치에 푸시한다.

예시 명령어:

```bash
cp templates/decisions/product.md decisions/product/YYYY-MM-DD-title.md
# 문서 작성 후
git add .
git commit -m "docs(decisions): add decision record"
git push origin main
```

## 결정 변경 규칙

- 결정의 의미가 바뀌는 경우 기존 문서를 직접 고치지 않고 새 결정 문서를 작성한다.
- 기존 문서는 상태를 `대체`로 변경하고, 새 문서를 관련 문서에 연결한다.
- 오탈자, 링크 수정, 표현 보완처럼 결정 내용이 바뀌지 않는 수정은 기존 문서에 반영할 수 있다.
